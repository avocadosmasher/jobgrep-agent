# UC-1 레벨 측정 질문 세트 (H2 체크포인트)

> 설계도 v2 §3(UC-1 레벨 좌표 측정) · §7-4(직군 프리셋) · §9-3 H2 의 구현 명세.
> 이 문서는 **직군 무관·1회** 실행되는 프로필 구축의 레벨 측정 부분이며, 산출물은 `ProfileJSON.level_coordinates`(§10-2)다.

---

## 1. 목적과 원칙

레벨 측정은 이력서·GitHub에서 **추출된 역량 원자에 깊이(레벨) 좌표를 찍는 일**이다. 두 가지를 동시에 한다.

1. **깊이 보정** — 이력서에 "K8s 경험"이라고만 적혀 있으면 그게 튜토리얼인지 운영인지 알 수 없다. 그 좌표를 확정한다.
2. **폭 보완** — 이력서에 안 적혔지만 해봤을 수 있는 역량을 프리셋 축으로 훑어 빠뜨린 것을 줍는다.

**세 가지 불변 원칙**

- **행동 기준(behavior-anchored)만.** "쿠버네티스 얼마나 잘하세요(1~5)" 같은 자기평가 척도 금지(§4 성향 진단 배제). 모든 선택지는 "무엇을 해봤는가"의 행동 마커다.
- **추출 결과로 사전 채움(pre-fill).** 이력서에서 이미 뽑힌 역량은 시스템이 레벨을 **추정해 미리 선택**해두고, 사용자는 확인·수정만 한다. 폼 길이를 줄이는 핵심.
- **해당 없음도 정보다.** "안 해봤음/모름"은 레벨 0이 아니라 **커버리지 계산의 입력**이다(§12-1 UC-1 하드 게이트).

## 2. 공통 4단계 레벨 사다리 (모든 역량에 동일 적용)

| 레벨 | 한 줄 정의 | 판별의 핵심 질문 |
| --- | --- | --- |
| **학습함** | 강의·튜토리얼·개인 학습으로 개념을 안다. 실제 과업에 쓴 적은 없거나 토이 수준 | "돌아가는 결과물을 만든 적이 있는가?" → **아니오** |
| **써봄** | 실제 프로젝트(개인·팀·과제)에서 동작시켜봤다. 남이 만든 틀 안에서, 막히면 검색·도움으로 해결 | "운영/장애 책임을 져봤는가?" → **아니오** |
| **실무 운영** | 실제 서비스·지속 운영 환경에서 이걸 책임지고 굴려봤다. 장애·트러블슈팅·튜닝 경험 있음 | "구조를 정하거나 도입을 주도했는가?" → **아니오** |
| **설계·주도** | 요구사항에서부터 구성/아키텍처를 **설계**했거나, 도입·마이그레이션·표준을 **주도**했다. 남을 가르치거나 의사결정을 이끌었다 | (사다리 최상단) |

**세 개의 승급 관문** (레벨을 가르는 유일한 기준)

```
학습함 ─[돌아가는 결과물을 만들었는가?]→ 써봄
써봄  ─[운영·장애·트러블슈팅을 책임졌는가?]→ 실무 운영
실무운영 ─[0→1 설계 또는 도입/표준을 주도했는가?]→ 설계·주도
```

**자기평가 인플레이션 함정 (측정 시 주의)**

- 가장 부풀려지는 관문은 **써봄 → 실무 운영**과 **실무 운영 → 설계·주도**다.
- "회사에서 K8s 썼어요"는 대부분 **써봄**이다. **장애를 직접 잡았거나 튜닝했어야** 실무 운영.
- "마이크로서비스 구조에서 개발했어요"는 **써봄**이다. **그 구조를 내가 정했어야** 설계·주도.
- 그래서 선택지 라벨을 "얼마나"가 아니라 위 관문의 행동으로 못박는다.

## 3. 측정 메커니즘

| 항목 | 방식 |
| --- | --- |
| 형태 | `st.form` **배치** — 대분류별 섹션, 각 역량 축 = 1개 라디오(해당없음 + 4레벨) |
| 선택지 라벨 | 아래 §4 표의 **대분류별 행동 마커**를 그대로 라디오 옵션 텍스트로 사용 |
| 사전 채움 | 추출된 역량은 시스템 추정 레벨을 pre-select, 미추출 축은 "해당 없음"으로 시작 |
| 문항 수 | 대분류 5개 × 축 5~6개 ≈ **25~30문항**(1회성 프로필이므로 감내 범위). pre-fill로 실제 입력 부담↓ |
| 근거 옵션(권장) | 각 "실무 운영/설계·주도" 선택 시 **한 줄 근거 입력란**(어떤 프로젝트에서) — §7 근거 규칙과 정합, 델타 인터뷰(UC-2) 부담을 앞당겨 줄임 |
| 산출 | `level_coordinates: {역량명 → 레벨}` + `coverage: {D1~D5 → 응답한 축 비율}` |
| 게이트 | coverage가 §12-1 UC-1 하드 요건 미달이면 프로필 `미완성` 표시 |

> **왜 근거란을 권장하나:** UC-1에서 "실무 운영/설계·주도"를 고를 때 한 줄 근거를 받아두면, UC-2 매칭 시 그 역량이 JD 기준을 넘는지 **재질문 없이** 판정 가능한 경우가 늘어 델타 인터뷰(§12-4)가 짧아진다. 선택이지만 강력히 권장.

## 5. D5 재보정 노트 (중요)

사용자 정의 = **"AI 워크로드를 돌리기 위한 인프라."** 따라서 D5의 무게중심은 **플랫폼·시스템 쪽**이다.

- **포함(중심):** GPU 자원·스케줄링, 분산 학습 **실행 환경**, 서빙·추론 **인프라**, 가속기 관측성, 고속 스토리지·네트워킹(InfiniBand/RDMA 포함 가능).
- **경계로 미룸(모델링·데이터과학 쪽):** 모델 아키텍처 설계, 하이퍼파라미터 튜닝, 실험 추적(MLflow) 자체 — 이는 D5 **중심이 아니라 인접**. 순수 실험 관리 역량이 강하면 별도 D6("MLOps·실험 파이프라인")로 분리 검토(현재는 D5에 소프트하게 포함).

> **설계도 반영 제안:** v2 §7-4의 D5 예시 중 "MLflow 실험 관리"는 이 재보정과 살짝 어긋난다. §7-4 D5 예시를 "GPU 클러스터 스케줄링, 분산 학습 실행 환경, 모델 서빙 인프라, 추론 최적화, 가속기 관측성" 중심으로 바꾸고, MLflow는 D6 후보로 잔여 처리하는 게 일관적. (원하면 반영)

## 6. 채점 → 좌표 매핑

```
각 역량 축 응답 →
  "해당 없음"      : level_coordinates에 미기록 + coverage 미충족으로 카운트
  학습함/써봄/…    : level_coordinates[역량명] = 레벨 (원문 역량명 보존, §7)
  (근거 입력 시)   : evidence[역량명] = 사용자 서술 → UC-2 델타 인터뷰 축소

대분류별 coverage = (응답한 축 수 / 그 대분류 축 총수)
  → §12-1 UC-1 하드 요건 게이트 입력
  → 커버리지 낮은 대분류는 "이 영역은 프로필이 얕음" 경고
```

**레벨 인코딩**(집계·비교용): 학습함=1 · 써봄=2 · 실무 운영=3 · 설계·주도=4.
단, 이 숫자는 **UC-2 매칭의 후보 추림·표시**에만 쓰고, **최종 판정에는 쓰지 않는다**(§7-2 원칙: 정량값은 판정 근거 아님). 판정은 여전히 기준 분해 + 근거 인용으로 한다.
